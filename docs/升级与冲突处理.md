# 升级与冲突处理

> 本套件的每一个修复都依赖某个"当时成立的事实"。**这些事实 dsh 一升级就可能变**，
> 而它们失效的方式全都是**静默的**：配置在、文件在、脚本不报错 —— 只是不再生效。
>
> 所以本手册的核心不是"记住正确配置"，而是**"知道怎么重新验证它"**。

## 0. 一句话原则

> **本套件不记录"事实"，只记录"如何重新推导事实"。**

落实到代码里的三条硬约束（改 `tools/doctor.mjs` 时必须遵守）：

1. **不写死路径** —— 用户全局指令文件叫什么，是**从已安装的 dsh 源码现推**的
   （`@deepseek-ai/dsh-agent-instructions/lib/index.js` 里的 `USER_GLOBAL_FILE`），
   不是我记得的 `AGENTS.md`。
2. **不维护映射表** —— "哪个 section 归哪个插件"是**现搜**出来的，不是一张表。
   *这条是有代价学来的*：我初版真写了一张表（`ui-theme` → `@deepseek-ai/dsh-ui-theme`），
   实测**是错的**，真正的属主是 `dsh-client-ui-theme`。**那张表本身就是一条会过期的记忆。**
3. **推不出来就报 `UNVERIFIABLE`，不许报 OK** —— 报"我不知道"比给一个假的绿灯安全得多。

## 1. 出问题先跑这一条

```bash
node tools/doctor.mjs
```

18 项检查，覆盖：环境 / dsh 版本漂移 / 全局指令文件路径 / 规则块是否就位 /
preset 副本指纹 / 默认 preset 是否存在 / 护栏是否落位 / 第三方子代理插件护栏 /
settings 段是否真被接线 / 档位合法性 / 分析脚本前置条件 / 仓库编码换行。

### 状态语义

| 状态 | 含义 | 要做什么 |
|---|---|---|
| ✅ `OK` | 已验证通过 | 不用管 |
| ⚠️ `WARN` | 能跑，但有风险或环境偏差 | 看一眼说明，通常无害 |
| ❌ `FAIL` | 断言被推翻，**会静默失效** | **必修**，退出码 1 |
| 🕳️ `INERT` | 配置在，但没有任何插件接线 → **存在但不生效** | 确认该由谁加载 |
| ❓ `UNVERIFIABLE` | 无法再验证这条断言（dsh 内部实现变了） | **人工确认**，别当通过 |
| ⏭️ `SKIP` | 前置条件不满足，本次跳过 | 通常无需处理 |

### 参数

| 参数 | 用途 |
|---|---|
| `--json` | 机器可读（CI 用）；含 `summary` 与逐项 `checks` |
| `--strict` | `WARN`/`INERT` 也算失败 —— 发布前用 |
| `--fix-safe` | 只做**幂等且带备份**的自动修复，然后**必须再跑一次确认** |
| `--profile <name>` | 指定"活的" profile（默认按 node_modules 的 mtime 猜，**是启发式**） |
| `--rescan` | 强制重扫"谁引用了哪个 settings 段"（否则走缓存） |

## 2. 症状 → 检查项 → 修法（对照表）

| 你观察到的症状 | 对应的检查项 | 根因 | 修法 |
|---|---|---|---|
| 升级 dsh 后规则全都不生效 | `dsh.drift` + `instruction.global-path` | 全局指令文件路径或规则块丢了 | `--fix-safe`，再人工看 `UNVERIFIABLE` |
| 明明改了 preset 却没效果 | `plugin.subagent-guard` | **护栏落在了没被加载的那一层**（插件接管了工具名） | 见 §4.3 |
| 某个 settings 段改了没反应 | `settings.wiring` = `INERT` | **没有插件接线**（插件没装在当前 profile） | 见 §4.4 |
| 子代理还是会无限派子代理 | `preset.leash` | 默认 preset 缺护栏 | `node tools/harden-preset.mjs "<preset目录>"` |
| `standard-leash` 一升级就怪怪的 | `preset.source-fingerprint` = `FAIL` | 副本是 shipped preset 的**拷贝**，源变了副本必然漂移 | `node tools/regen-standard-leash.mjs` |
| 分析脚本报 0 条会话 | `scripts.preflight` | 日志目录形状变了，或没解压后端 | 见 §4.5 |
| 脚本抛 `'gbk' codec can't encode '\xa5'` | `repo.encoding` | Windows 重定向 stdout 用了本地代码页 | `node tools/check-encoding.mjs --fix` |
| PowerShell 报 `missing the terminator` | `repo.encoding` | `.ps1` 丢了 UTF-8 BOM，PS 5.1 在代码页 936 下按 GBK 读 | `node tools/check-encoding.mjs --fix` |
| Ubuntu 上 `bash: ./install.sh: bad interpreter` | `repo.encoding` | `.sh` 被 `core.autocrlf` 转成了 CRLF | `node tools/check-encoding.mjs --fix` |
| 启动就报 `UNSUPPORTED_REASONING_EFFORT` | `effort.legality` | 档位是**按模型**算的，写错启动不报错 | `node tools/show-effort-levels.mjs --current` |
| 某条规则"好像生效又好像没生效" | `instruction.stale-twin` | 存在**影子指令文件**（DSH 不读的那个路径） | 人工合并或删除 |

## 3. 升级 dsh 之后必做（标准流程）

```bash
# 1. 升级（本套件的安装脚本**默认不会**替你升级，要显式 -UpgradeDsh / --upgrade-dsh）
npm install -g @deepseek-ai/dsh

# 2. 巡检：这一步会报 dsh.drift WARN，提醒"所有指纹都可能已失效"
cd <本仓库>
node tools/doctor.mjs

# 3. 按 FAIL 逐条修。其中两条可以安全自动修：
node tools/doctor.mjs --fix-safe

# 4. 重启 dsh web（preset / 插件类改动需要重载 profile 才生效）

# 5. **再跑一次确认** —— 修复本身也要被验证
node tools/doctor.mjs
```

> 第 5 步不能省。`--fix-safe` 的输出只是"我执行了修复"，不代表"修复生效了"。
> 这与本仓库踩过的那个坑同类：**干跑只能验证"打印了什么"，验证不了"真调用了什么"。**

## 4. 五类真实冲突详解

### 4.1 preset 副本漂移（**必然发生**，不是故障）

`presets/standard-leash/agent.cordis.yml` = 已装 dsh 的 shipped `standard` preset
**逐字节副本** + 两处注入。**源变了，副本就漂移** —— 这是设计使然，不是 bug。

- 检测：`preset.source-fingerprint`（比较 `SOURCE.txt` 里记的 sha256 与当前 shipped preset 的 sha256）
- 修法：`node tools/regen-standard-leash.mjs`（重新生成，并更新 `SOURCE.txt` 指纹）
- 历史教训：这份副本**曾经是一份手工维护的过期副本**，README 还谎称"逐字节副本、只改了两行"，
  实际还缺 `command-goal` / `present` / `modelSelectionSettings: true` / `fetch: true`。
  **直接部署它会静默削掉 agent 的工具。** 现在副本由脚本生成 + sha256 指纹，就是为了让漂移**可见**。

### 4.2 全局指令文件路径变了（规则静默失效）

- 症状：`~/.dsh/AGENTS.md` 里明明写着 6 条规则，但会话里完全看不到。
- 检测：`instruction.global-path` —— 从 `dsh-agent-instructions/lib/index.js` 现推
  `USER_GLOBAL_FILE`。**推不出来就报 `UNVERIFIABLE` 并给出要看的文件路径**，不猜。
- 历史教训：本仓库文档**曾经教人写 `~/AGENTS.md`，而 DSH 从不读那个路径** ——
  按原文档装完，6 条规则一条都不会进上下文。本机现在那个影子文件还在（见 `instruction.stale-twin`）。

### 4.3 护栏落在了**没被加载的那一层**（最隐蔽）

- 症状：`toolFilter.deny` 里明明写了 `subagent`，子代理照样能再派子代理。
- 根因：`@huanlin/dsh-plugin-yet-another-subagent` **接管了 `subagent` 这个工具名**，
  把官方那条 spawn 路径 disable 了。写在 cordis preset 里的 `toolFilter` **属于另一层**，对它无效。
  护栏必须写进**插件自己的设置命名空间**（`ya-subagent`）。
- 检测：`plugin.subagent-guard`（用插件**自己的 schema** 校验，含负例反证）+
  `plugin.delegation-surface`（泛化：扫出所有名字像委派面的插件，提醒你它们可能又开了一条路）
- 修法：见 `docs/本地插件与治理融合.md` §1；然后 `node tools/check-ya-subagent.mjs` 确认

### 4.4 `settings.yaml` 的段**存在但不生效**（INERT）

- 症状：改了 `spill-policy.maxInlineBytes`，行为没变。
- 根因：`settings.yaml` 的 section **只有插件主动接线才生效**。
  段在文件里 ≠ 有插件读它。插件没装在**当前 profile** 下，段就是死的。
- 检测：`settings.wiring` —— 扫遍所有已安装的包，看谁的代码里出现了这个 key。
  **证据强度是不对称的，这点必须记住：**
  - 没有任何包提到这个 key → **强证据**：该段极可能完全没生效
  - 有包提到这个 key → **弱证据**：只能证明"有人提到过"。
    实测 `llm-pi-ai` 会命中 `dsh-authorization`，`spill-policy` 会命中客户端 UI ——
    它们只是提到了这个名字，不代表它们负责接线。
- 修法：确认该段该由哪个插件加载；把它写进**真正接管它的插件自己的设置命名空间**。

### 4.5 分析脚本静默报 0

- 症状：`weekly_review.py` 跑出来"0 条会话"，不报错。
- 根因有两种，都可能随 dsh 升级出现：
  1. 会话日志目录形状变了（脚本 glob 的是 `$DSH_HOME/sessions/*/*/session.jsonl.zstd`）
  2. 解压后端没了或换了
- 检测：`scripts.preflight`（数日志条数 + 探测 `python -c "import zstandard"` / `zstdcat` / `zstd` / `uv`）
- 修法：
  - 形状变了 → 更新 `scripts/_session_io.py` 的 `session_glob()`
  - 只是解释器问题（Windows 常态：`python` 是 Microsoft Store 占位器）→ 用 uv 兜底：
    `uv run --no-project --python 3.12 --with zstandard python scripts/weekly_review.py`
  - 注意这里**故意不把"裸 python 不行"判成 FAIL** —— 那会让一台其实健康的机器一直红着，
    久了就没人看红色了。只有"连 uv 都没有"才判 FAIL。

## 5. 升级后需要**人工确认**的部分（无法自动验证）

`doctor` 会把这些标成 `UNVERIFIABLE`，那**不是**通过：

1. **dsh 内部实现变了** —— 例如 `dsh-agent-instructions` 里不再有 `USER_GLOBAL_FILE` 常量。
   doctor 会给出要看的文件路径。这种情况下**不要**直接改 doctor 去"适配"，
   先确认 dsh 的新机制是什么。
2. **`dsh.drift` 的 history** —— 状态文件里记录了每次 dsh 版本变化。
   连续升级后，如果某项一直没人修，它会一直红着；**红着不修等于没有这项检查**。
3. **第三方插件的工具名** —— 插件更新后可能新增工具名。
   `plugin.delegation-surface` 只能靠**名字**提示，权威答案在合成后的配置里：
   `dsh --profile <name> --dump-config`

## 6. 本套件的状态文件

```jsonc
// $DSH_HOME/.dsh-migration-kit.json   （Windows: %USERPROFILE%\.dsh\...）
{
  "kitVersion": 2,
  "dshVersion": "0.1.5-rc.2",          // 上次巡检时的 dsh 版本 → 用于漂移检测
  "shippedStandardSha256": "08a029…",  // 上次 shipped standard preset 的 sha256
  "activeProfile": "web-3",
  "wiringCache": {                      // "谁引用了哪个 settings 段"
    "key": "0.1.5-rc.2|web-3|ui-onboarding,llm-pi-ai,…",   // ← 含版本+profile+段名集合
    "owners": { "compaction-acp": ["billion-context-dsh"] }
  },
  "history": [ { "at": "…", "from": "0.1.4", "to": "0.1.5-rc.2" } ],
  "lastSummary": { "ok": 15, "warn": 3, "fail": 0, "inert": 0, "unverifiable": 0 }
}
```

**缓存必须带失效键。** 缓存的 key 里含 `dsh 版本 + profile + settings 段名集合`，
任一项变化都会自动失效 —— 否则缓存就变成**一条新的"会过期的记忆"**，
正好是本文件开头那条原则要消灭的东西。

删除这个文件是安全的：doctor 会把它当成"首次运行"，重新建立基线（并提醒一次）。

## 7. 已知的、**尚未**被覆盖的失效模式

诚实清单 —— 这些目前只能靠人：

1. **`install.sh` / `launcher/dsh-web.sh` 从未在真实 Linux 上执行过**
   （本机无 WSL）。**`bash -n` 已过**（2026-09-19：沙箱放宽后实测两个文件
   `bash -n` 均 exit 0，这是它们第一次被真正语法校验），但语法正确 ≠ 能装成功：
   里面涉及 `~/.config/rtk` 路径、XDG、发行版差异、下载 rtk 二进制等
   只能在真机上验证的环节。
   doctor **不检查**这两条 —— 它没有能力判断"没跑过的脚本是对的"。
2. **插件内部行为变化** —— 插件更新后 `settings` 段的语义可能变（不是消失，是改含义）。
   doctor 只能看"有没有人引用这个 key"，看不出"引用它的代码逻辑变没变"。
3. **`UNVERIFIABLE` 项不会自动变绿** —— 它们需要人去看一眼 dsh 的新实现。
4. **doctor 自己也会过期** —— 它推导事实的**方法**（正则、文件位置）也可能失效，
   那时它会报 `UNVERIFIABLE` 而不是撒谎。**看到 `UNVERIFIABLE` 变多，就是该修 doctor 的信号。**
