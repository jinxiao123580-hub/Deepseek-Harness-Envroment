# 交接体系（handoff / succession）

**一句话**：长任务在上下文变长之前"换人"——写出便条级交接文档 → 开一个新的顶层会话继续 → 旧会话冻结。

不是"接着聊"，也**不是** compaction（压缩是同一会话内原地重写历史）。

---

## 1. 为什么不用 compaction 兜底 [外部证据]

| 事实 | 数字 | 来源 |
|---|---|---|
| 摘要 vs 直接丢弃旧观测：**摘要没赢** | SWE-bench Verified 解题率 53.8% vs 54.8%，单例 $0.64 vs $0.61 | arXiv 2508.21433 |
| 少给历史反而更好 | SWE-agent：全历史 15.0% vs 只留最近 5 条观测 **18.0%** | arXiv 2405.15793 |
| compaction 砸掉前缀缓存（生产） | 触发于 7.8% 会话却覆盖 44.2% token；prompt token 中位 −72.8%；**缓存命中率中位 −66.1%**，34.3% 事件抹掉 ≥90% | arXiv 2608.00101 |
| compaction 丢事实 | 一次 36.7× 压缩后 **60% 事实不可恢复**；项目约束 91% → 62% → 46% | arXiv 2603.17781 |
| "被自己旧结论困住"是实测现象 | GPT-4 单独看能识别错误论断 **87.03%**，放进上下文后正确率仅 **16.6%** | arXiv 2305.13534 |
| 多轮对话整体退化 | 15 个模型平均 **−39%**，不可靠性 **+112%** | arXiv 2505.06120 |
| 自我批判不如外部验证 | 55% vs **88%** | arXiv 2310.08118 |

**反向证据也必须记录**：Amp 于 2025-10-23 上线 Handoff（"no more compaction"），
**2026-05 又删掉 Handoff、改回自动 compaction**；Anthropic 报告 Sonnet 4.5 时代
"compaction alone wasn't sufficient，context resets became essential"，到 Opus 4.5 又不再需要。
→ 所以这是**模型/规模相关**的结论，必须用自家数据每周复核。

完整 ADR：`handoff/adr/0001-handoff-over-compaction.md`

## 2. 三个词，别混

| 词 | 含义 | 代价 |
|---|---|---|
| **交接 succession** | 换一个**新的顶层会话**继续，旧会话冻结 | 写 INDEX + 继任者冷启动 ≈ **¥0.07**（实测） |
| **委派 delegation** | 主会话不变，派子代理干活 | 多起一整条 agent 循环（39 步 × high 档 = ¥0.4–1.6/任务） |
| **压缩 compaction** | 原地重写历史（同一会话） | 见上：打掉缓存 + 丢事实 |

## 3. 交接文档（INDEX）：便条级，不是报告

六字段，缺一不可：**目标 / 已完成（结果 + 证据路径）/ 未决 / 下一步 / 硬约束 / 验证方式**，外加"去哪找"的指针。

- 上限 **≤70 行、≤1.5 k tokens**；禁止贴代码/日志/原文。
- 要超了**先砍"历史过程"**（修过哪些 bug、怎么试的），**绝不砍**硬约束、验证命令、证据路径、状态标记。
- 每条判断句必须标 **`[有效]` / `[存疑]` / `[已否证]`**：
  - `[有效]` 必须附**证据**路径（输出文件/测试结果/日志），**不能附脚本或源码路径**。
  - `[存疑]` 可以照做，但**不得当作前提继续推导**。
  - `[已否证]` 必须留档（错在哪、为什么错），防止下一个人重犯。

> 为什么容得下 1.5 k tokens：多出的 ~360 tokens 在继任会话 50 轮里约 **¥0.0003**；
> 而一个错文件名会让继任者多跑一次失败命令 + 重试循环 ≈ **¥0.02–0.05**。**精度比字数便宜两个数量级。**
> 真正要抠的是"把内容抄进来"——那才是每轮都在付费的部分。

## 4. 交接流程

```
旧会话（趁热，缓存还在）          新会话（继任）
─────────────────────────       ─────────────────────────
用户说「交接」
  → 读 handoff/README.md
  → 写 .handoff/<MMDD-HHMM>-<slug>/INDEX.md
  → 告诉用户"新会话选哪个档位"
  → 冻结（不再推进任务）
                                用户开新会话（档位 off/high）
                                  → 说「读 <INDEX 绝对路径>，按它继续」
                                  → 首轮：读 INDEX → 核验 1 条 [有效] → 报告可开工性
```

**成本模型**（实测校准）：

| 项 | 值 |
|---|---|
| 写 INDEX | ≈ ¥0.016（2 k 输出） |
| 继任者冷启动 + 首轮核验 | **¥0.068**（实测：17 请求 / 23 工具调用 / 终态 30 k） |
| 不交接继续跑 | 250 k 上下文时 **¥0.02–0.04/步** |

→ **只剩 5–15 步活时就该交接**；剩 <10 步就直接干完；任务不要了就弃（交接也有成本）。

**时机**：趁热交接最便宜。会话刚活动过 → 600 k 上下文读一遍只 ≈ ¥0.02；闲置数小时后缓存过期 → **¥0.6–1.2**，还要多等一次长请求。

## 5. 继任者纪律

- **检索预算**：一轮 ≤15 次工具调用、网页 ≤2 次；超了先问用户。
  （这条**必须写在 INDEX 头部**——继任者只读 INDEX，不会去读 README。）
- **本地优先**：`grep`/`read` → 项目文档 → `.handoff/` 旧件 → 兜底才联网。
- **禁止**无差别重读旧会话全文（那等于把省下来的上下文又买回来）。
- 想验证交接质量时，可用"只读自检"一轮（见 `handoff/README.md` §10）：复述 + 核验 1 条 + 指出矛盾 + 回答能否开工。

## 6. 档位（reasoning effort）规则

DeepSeek 线只有 `off` / `high` / `max`（`low`/`medium` 会被适配器拒绝）。

- **会话起始就定档**：执行型 `off`，决策型 `high`。
- **换档只在会话 <30 k 时做一次**（那时首次启用新档位 ≈ ¥0.06）；250 k 时首次启用 = **¥0.5 + 多等 ~20 s**。
- **绝不按轮次切档**（每个档位是独立缓存谱系）。
- `max` 不常设；用则**显式压 `max_tokens`**（该档默认抬到 128 K）。
- **模型无权改自己的档位** → 只能"按任务把活分给不同档位的子代理"，或由用户换档。
  详见 `handoff/README.md` §6 的三种形态表。

## 8. 验收与回滚

```bash
python3 scripts/verify_leash.py     # 新会话里派过一次 subagent 后跑，期望 PASS
python3 scripts/weekly_review.py    # 每周一次，输出到 .handoff/review/<日期>.md
```

**回滚**：`~/.dsh/settings.yaml` 里 `agent-presets.default` 改回 `standard`；preset 只影响新会话。

**已知未验证项**：子代理 `persona` 需要一次真实 `subagent` 派发才能确认（`verify_leash.py` 会标 PENDING）。
