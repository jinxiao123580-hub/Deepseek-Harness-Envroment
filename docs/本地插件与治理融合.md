# 本地插件与治理融合

> 2026-09-19 实查。**本文是"本机已装插件"与"本套治理方案"如何共存的权威记录。**
> 一句话结论：**本机的治理能力被两个本地插件重新分层了 —— kit 写在
> `agent-presets/*.agent.cordis.yml` 与 `settings.yaml` 的东西，有一半根本没生效。**

## 0. 先确定"活的"是哪个 profile（一切结论的前提）

本机装了 5 个 profile（`headless` / `qq` / `web` / `web-2` / `web-3`），
**它们装的插件完全不同**，所以"我改了配置"这句话必须先说清改的是哪个。

判定方法（别猜，看进程）：

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*--profile*' } |
  ForEach-Object { if ($_.CommandLine -match '--profile\s+(\S+)') { "PID $($_.ProcessId) -> $($matches[1])" } }
```

本次实测：**`--profile web-3`**（`dsh --profile web-3 --port 0 --no-open`）。
旁证：`billion-context-dsh` 只装在 web-3，而 `settings.yaml` 的 `compaction-acp`
注释引用的正是 `profiles\web-3\node_modules\billion-context-dsh\...`。

## 1. 【最重要】子代理护栏原来落在**没有加载的那一层**

### 现象
`~/.dsh/.agent-presets/router-standard/agent.cordis.yml` 里 `tool-subagent` 与
`tool-subagent-fork` 两行带着 4 项护栏（`maxDepth: 1` / `agentOptions` 降档
`deepseek-cheap` / `toolFilter.deny` / `persona`）。**但在 web-3 上这些对
`subagent` 工具毫无作用。**

### 原因
web-3 装了 `@huanlin/dsh-plugin-yet-another-subagent` v0.4.3，它自带的
`cordis.patch.yml` 把官方插件**关掉并接管了工具名**：

```yaml
# Disable official tool-subagent (spawn path; this plugin takes over the
# `subagent` tool name).
- id: tool-subagent
  disabled: true
- insert:
    - id: yet-another-subagent
      name: '@huanlin/dsh-plugin-yet-another-subagent'
      config:
        profiles:
          - id: general
            model:      { kind: 'auto' }      # 不降档 → 子代理走默认模型
            persona:    { kind: 'inherit' }   # 没有护栏 persona
            toolFilter: { kind: 'none' }      # 不限工具
            maxDepth: 3                       # 深度 3
        generalFixed: true
```

### 两个独立验证（不是读注释得出的结论）
1. **官方行确实被关**：`dsh --profile web-3 --dump-config` 里
   `- id: tool-subagent` / `name: '@deepseek-ai/dsh-tool-subagent'` 带 `disabled: true`。
2. **接管确实发生**：本会话 `subagent` 工具的描述是 profile 式
   （`Available profiles: - "general": General`），而官方 `dsh-tool-subagent`
   没有 profile 概念（它是 `provider: spawn`）。

⇒ 之前 `weekly_review.py` 报出的 `depth {0:5, 1:9, 2:1}` 不是异常，
而是 `maxDepth: 3` 的正常表现；`model: auto` 意味着**子代理没有降档**，
这正是那 ¥8.34 扇出事故的成本结构。**"护栏已部署"当时是假的。**

### 修法（已执行）：写进插件自己的设置命名空间
`settings.yaml` 的 **`ya-subagent`** 段。依据全部来自源码：

- 命名空间常量取自插件自己的导出：
  `lib/index.js` → `SETTINGS_NAMESPACE = "ya-subagent"`
- 持久化位置见插件 docstring（`lib/types/profile-store.d.ts`）：
  > "Backed by `ctx.settings` when a settings service is mounted (persists to
  > `$DSH_HOME/settings.yaml` under the `ya-subagent` namespace)"
- 形状经过插件自己的 `Config` schema 校验通过（**并做负例反证**：
  `maxDepth: -1` 被拒 → `expected number >= 0 but got -1`，说明"通过"有意义）
- 该插件的 `Config` 字面形状（`String(Config)` 实测）：
  ```
  { profiles?: { id, label, model: { kind: "auto"|"manual", provider?, model? },
                 persona?: { kind?: "inherit"|"custom", text? },
                 toolFilter?: { kind?: "none"|"allow"|"deny", tools? },
                 maxDepth?, backgroundMode?: "continuable"|"one-shot", builtin? }[],
    generalFixed?: boolean }
  ```

**生效时机**：插件在加载 profile 时读该 section ⇒ 需要**重载 profile / 重启 dsh web**。
**代价**：若在该插件的 Web 设置页增删改 profile，settings 层是 section 级的 → 整段写回，
可能覆盖护栏，届时重贴。回滚：
`cp ~/.dsh/settings.yaml.bak-yasubagent-<stamp> ~/.dsh/settings.yaml`。

> 注意一个**不对称**：`subagent_fork` 仍由官方 `tool-subagent-fork` 提供，
> 所以 `router-standard` 里那一行的护栏**应该是生效的** —— 也就是
> "fork 出去的孩子被拴住，spawn 出去的孩子没有"。修好之后两者才一致。

## 2. 【同样重要】`settings.yaml` 的 section **只有插件主动接线才生效**

### 机制（读源码确认）
让 settings 进插件 config 的唯一途径是插件自己调用：

```js
settingsCtx.settings.installSection(ctx, NAMESPACE, SCHEMA, entry, hooks)
```

全量扫描本机安装后，**只有这些插件调了**：
`dsh-agent-default-model:45`、`dsh-agent-loop:1520`、`dsh-bash-local:148`、
`dsh-llm-deepseek:2080`、`dsh-llm-pi-ai:2661`、`dsh-permission-presets:123`、
`dsh-pwsh-local:230`（另有 `dsh-agent-presets` 用 `settings.register`）。
第三方插件（如 `billion-context-dsh`）在自己的代码里做同样的接线，
其 docstring 明说："Wires the engine's scalar knobs into the host's user-settings
layer (~/.dsh/settings.yaml, section `compaction-acp`) ... so editing the file
applies to RUNNING sessions without a restart."

⇒ **没有调 `installSection` 的插件，settings.yaml 里同名 section 是死配置**
（不会报错，静静被忽略 —— 这是最坏的一种失败方式）。

### 实测：本机 `settings.yaml` 三个调优项，只有一个是真生效的

| settings.yaml 里的段 | 是否生效 | 依据 |
|---|---|---|
| `compaction-acp.modelContextLimit: 250000` | ✅ **生效** | ACP 自己接线（其 docstring） |
| `compaction-basic.thresholdRatio: 0.45` | ❌ **不生效** | 该插件在 web-3 里 `disabled: true` |
| `spill-policy.maxInlineBytes: 8192` | ❌ **不生效**，真实值 **50000** | 该插件整棵树里 `installSection`/`settings.register`/`ctx.settings` **零命中** |

`spill-policy` 的真实值来自 `dsh-base/cordis.patch.yml:383`：

```yaml
- id: spill-policy
  name: '@deepseek-ai/dsh-spill-policy'
  config:
    maxInlineBytes: 50000
```

**后果**：8 KB ~ 50 KB 的工具输出**仍然整段留在上下文里**，并被之后每一轮重复计费 ——
这正是 `maxInlineBytes` 想压住的那部分成本（用户的 8192 意图是对的，只是没落地）。

### 怎么改才对
`spill-policy` 没有 settings 接线，所以**必须改 cordis 层**，即 profile 自己的
patch 文件（用户可写、不会被插件升级覆盖）：

```
~/.dsh/profiles/web-3/cordis.patch.yml
```

在其中对 `spill-policy` 条目覆盖 `config.maxInlineBytes`。
**注意**：该文件参与 profile 启动，写坏会导致 profile 起不来 ——
改前备份，改后用 `dsh --profile web-3 --dump-config` 确认合成结果无误。
同理 `compaction-basic` 在 web profile 下是被 `@deepseek-ai/dsh-web-app`
关掉的，想让它生效得先确认为什么关（**web profile 的设计就是交给 ACP**，
所以更合理的做法是**接受它被关，把调优只放在 ACP 上**，别再维护两套阈值）。

## 3. `dsh-context-doctor` 是本机上下文治理的正确主力（但有盲区）

本会话的 `context_audit` 工具就来自它（`dsh-context-doctor` v0.7.2，
"统计 AGENTS.md 指令链 / 技能目录 / 工具 schema / MCP 工具的 token 成本，检测重复与冲突"）。

**它比 kit 里自造的思路更全**，所以治理部分应以它为主：指令链、技能目录、
工具 schema、重复块、同名遮蔽（shadowed）、以及按 token 排序的裁剪建议。

**实测一次审计（cwd = `D:\Deepseek Harness`）**：

```
1. 指令链:  1 个文件 / 1.3k tokens
             D:\Deepseek Harness\CLAUDE.md (1.3k tokens / 5.0 KB)
2. 技能目录: 43 个技能 / 2.1k tokens
3. 工具 schema: 33 个可见工具 / 5.0k tokens（序列化 37.1 KB）
5. 建议: 0 条
```

### ⚠️ 它的盲区（实测发现，必须记住）
**它没报 `~/.dsh/AGENTS.md`。** 那正是本套方案部署的 6 条规则所在的文件
（1622 B），而且它**每轮请求都在付 context 租**。原因是该工具按 `cwd`
扫项目树，而用户全局指令文件在 cwd 之外。

⇒ 所以：**用 `context_audit` 看项目层的注入面，但用户全局层要自己算。**
要评估 `AGENTS.md` 的性价比，直接看它的字节数，并记住
"每轮都付" —— 这也是把规则块压到 15 行以内的原因。

## 附：一次"自己制造的"回归 —— 包名不是工具名

> 记录于 2026-09-19。这条比插件本身更值得留，因为**造护栏的动作本身就制造了故障**。

### 现象

给 `yet-another-subagent` 写护栏时，`toolFilter.deny` 被写成
`[subagent, subagent_general, subagent_fork, workflow, ralph]`。
其中 **`subagent_general` 是一个根本不存在的工具名** —— 按 `subagent_<profileId>` 的命名臆想编的。
真名只有 `subagent` / `subagent_fork`（来自合成配置的 `toolName:` 字段）。

后果是派子代理时直接抛（`dsh-tools/lib/index.js:2803`）：

```
Error: tools.restrict() names unknown global tool "subagent_general";
known global tools: acp_status, ..., subagent, subagent_fork, ..., write
```

⇒ **子代理彻底派不出去**，比"没护栏"更糟。

### 为什么静态检查看不出来

`restrict()` 只在**真正发起子代理时**才被调用。配置写得再错，`--dump-config` 也照样正常输出，
所以"看一眼配置文件对不对"永远发现不了 —— 这正是本套件一直强调的**静默失效**，
只不过这次是"静默锁死"。

### 更值得记的是：检查脚本当时在自证

`tools/check-ya-subagent.mjs` 初版第 148 行硬编码：

```js
const DENY_WANT = ['subagent', 'subagent_general', 'subagent_fork', 'workflow', 'ralph'];
```

第 192 行又把它回显成 `（子代理工具名：subagent / subagent_general）`。
也就是说 **检查在验证我自己的假设，却报告成事实**，而且是循环论证 —— 配置里那个假名字
正是脚本要求写的。这直接违反了本套件的第一原则"不记录事实，只记录如何重新推导"。

### 修法：工具名只认两个权威来源，包名只能当线索

| 来源 | 权威性 | 说明 |
|---|---|---|
| `--dump-config` 的 `toolName:` 字段 | **权威** | cordis 行自己声明的工具名 |
| `tools.restrict()` 报错里的 `known global tools:` | **权威** | 运行时注册表（`dsh-tools/lib/index.js:2801` 的 `restrictableNames`）；拿不到静态表，只能捕获一次并记下 dsh 版本，**版本一变即失效重取** |
| `dsh-tool-*` 包名 | **只是线索** | `dsh-tool-subagent-control` 的真实工具是 `send_message` / `interrupt_agent` / `list_agents`；`dsh-tool-subagent-list-agents` 对应 `list_agents`。**把包名当工具名会造成上面的锁死** |

捕获的观测存在 `$DSH_HOME/.dsh-ya-known-tools.json`（带 `dshVersion` / `capturedFrom` /
`howToRecapture`），dsh 升级后自动判失效并要求重取。

现在脚本分两个集合：`confirmed`（可安全写进 deny）与 `advisory`（仅线索，**永不**进入
"漏 deny"清单）。另新增硬错误 `denyUnknown`：deny 里出现未确认的名字 → FAIL，
并说明"子代理将完全派不出去"。这个检查如果早一天存在，这次回归就不会发生。

### 还有一个更隐蔽的坑：护栏要写在**生效的那一层**

插件的配置有两个来源：

1. `~/.dsh/profiles/<p>/cordis.patch.yml`（用户补丁层，进程启动时应用）
2. `~/.dsh/settings.yaml` 的 `ya-subagent:` 命名空间（插件把运行时配置**持久化**在这里，
   见插件 `profile-store.d.ts`）

实测：第一次只改了 `cordis.patch.yml`，**故障依旧** —— 因为生效的是 `settings.yaml` 那一层。
两层都要看，`--dump-config` 的合成结果才是唯一可信的画面。

> 生效需要**重载 profile / 重启 dsh**：运行中的进程缓存了旧的 profile store。
> 磁盘上的配置是否已正确，随时用 `node tools/check-ya-subagent.mjs` 确认。

### ✅ 2026-09-19 重启后的实测验证（结论按实测改口）

重启 dsh 后实测（新进程 PID 4600，监听 `127.0.0.1:61208`；出问题的旧进程是 PID 15164）：

| 现象 | 实测结果 |
|---|---|
| 派子代理 | **成功** —— `tools.restrict()` 那个 `unknown global tool` 报错消失了 |
| 子代理再派子代理 | **被拒**：`Error: subagent depth 2 exceeds maxDepth 1` |
| `workflow` / `ralph` 在子代理里 | **不可见**（探针实测：不在工具列表里） |
| `subagent` 在子代理里 | **仍然可见**，但调用会被深度锁拒掉 |

**所以之前那句"第二道锁让子代理连这些工具都看不见"是 overclaim，这里改口：**

- `maxDepth: 1` 是**第一道、也是真正兜住递归的那道锁**（实测生效）。
- `toolFilter.deny` 的实测效果目前只观察到覆盖 `workflow` / `ralph`（这两个确实从子代理
  工具面消失了）；**`subagent` 并没有被摘掉**，拦住它的是深度锁。

### 方法论教训：不要让子代理"自述工具列表"

同一条探针，两次结果**互相矛盾**：第一次子代理自述"可见 `subagent` / `workflow` / `ralph`"，
第二次自述"`workflow` / `ralph` 不可见"。而它自述的依据很可能只是**我在提示里列举的名字**
（我提问时就把这几个词写进去了），属于被引导出来的复述，不是观察。

⇒ 判断护栏是否生效，**只认可观察的调用结果**（成功 / 报错原文），
不要认"我的工具列表里有/没有 X"这种自述。这与本套件"不记录事实、只记录如何重新推导"是同一条原则：
**自述是声明，调用结果才是证据。**
