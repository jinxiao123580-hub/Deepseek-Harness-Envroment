## 二、Windows 平台问题

### 2.1 无 BOM 的 `.ps1` 在 Windows PowerShell 5.1 下直接语法报错 **[已修]**

本机 ANSI 代码页 = **936（GBK）**。README 让用户用 `powershell`（5.1）跑脚本，而
5.1 把**无 BOM** 的 `.ps1` 按 ANSI 解码 —— UTF-8 的中文字节被拆开，字符串引号会破掉，
报的是 `The string is missing the terminator: "` 或 `Unexpected token`。

git 里原本的提交**是带 BOM** 的（`EF BB BF`），是这次用文件工具重写时丢掉的 ——
也就是说**这个坑很容易在编辑过程中复发**。

**修法 [已修]**：`tools/check-encoding.mjs` 强制策略并已 `--fix`：

- `.ps1/.psm1/.psd1` → **必须**有 UTF-8 BOM；
- `.sh/.py/.js/.mjs/.yaml/.toml/.md/.cs/...` → **必须没有**（`.sh` 带 BOM 在 Linux 上
  会 `bad interpreter: required file not found`）。

### 2.2 Python 输出 `¥` 在重定向时崩溃 **[已修]**

```
UnicodeEncodeError: 'gbk' codec can't encode character '\xa5' in position ...
```

只在 **stdout 被重定向/管道**时出现：重定向走 locale 编解码器（936），而真实控制台走
`_WindowsConsoleIO`（utf-8）—— **所以交互式跑永远看不见这个 bug**，
但 `python x.py > out.txt`、`| tee`、CI 里 100% 崩。

**修法 [已修]**：`scripts/_console.py` 的 `setup()` 把所有脚本的 stdout/stderr
`reconfigure(encoding="utf-8", errors="replace")`。

### 2.3 Windows 没有 `zstd`，脚本硬调 `zstdcat` 直接挂 **[已修]**

`cost_anatomy.py:47`、`weekly_review.py:43`、`verify_leash.py:23` 都写
`subprocess.run(["zstdcat", f], ...)`，而且**只检查 `returncode`、不处理找不到二进制**。
Windows 上 `zstdcat`/`zstd` 都不存在 → `FileNotFoundError` 堆栈。

**修法 [已修]**：新增 `scripts/_session_io.py`，后端按
`python-zstandard` 模块 → `zstdcat` → `zstd -dc` 依次尝试，支持 `DSH_ZSTD` 环境覆盖，
`$DSH_HOME` 可覆盖根目录，全都没有时打印**可照做的安装提示**并 `sys.exit(1)`。
Windows 首选 `pip install zstandard`。

### 2.4 文档里的 `python3` 在 Windows 上不存在 **[已修]**

所有 docstring / usage 都写 `python3 scripts/...`。本机 `python` 与 `python3` **都**指向
Microsoft Store 的占位器（跑起来是 "Python was not found; run without arguments to install
from the Microsoft Store"），`py` 也不存在。

**修法 [已修]**：每个脚本的 docstring 同时给两平台写法；`cache_ttl.py` 里那句
POSIX-only 的 `nohup python3 ... > /tmp/ttl.log 2>&1 &` 补了 PowerShell `Start-Job` 版本。

### 2.5 `rtk/config.toml` 与 `filters.toml` 从来没被安装过 **[已修]**

`install.ps1` 只把 `rtk.exe` 放到 `~/.local/bin`，**从不复制** `config.toml` / `filters.toml`。
本机实测 `%APPDATA%\rtk\` 里**只有 `filters.toml`、没有 `config.toml`**。
RTK 会静默用默认配置 —— 包括它自己那些省略输出、丢日志的默认行为。

**修法 [已修]**：`install.ps1` 新增一步，把两个 toml 复制到 `%APPDATA%\rtk\`，
**已存在就跳过**（除非 `-ForceRtkConfig`），避免覆盖用户调过的配置。
`install.sh` 对应装到 `~/.config/rtk/`（XDG）。

### 2.6 PATH 只改了当前会话，README 却承诺"重开终端就有" **[已修]**

旧脚本第 76 行是 `$env:Path += ";$binDir"` —— 只影响**当前进程**。
而 `README.md` 承诺重开终端后 `rtk` 可用。

**修法 [已修]**：改成
`[Environment]::SetEnvironmentVariable("Path", $newPath, "User")` 持久化，
并带幂等检查（本机用户 PATH **已经**含 `C:\Users\10905\.local\bin`，所以这一步是 no-op —— 正确行为）。

### 2.7 `IsListening` 从不调 `EndConnect` —— 语义依赖时序 **[已修]**

```csharp
var result = client.BeginConnect("127.0.0.1", port, null, null);
return result.AsyncWaitHandle.WaitOne(300);   // EndConnect 从未调用
```

等待句柄在**异步操作完成**时被置位，**包括连接被拒绝**，所以它在语义上无法区分
"端口开着"和"端口关着"。一旦它返回 true，`Main` 就不会去启动 dsh，`PickProxy()` 还会
把一个**死掉的** `http://127.0.0.1:7897` 写进 `HTTPS_PROXY`/`HTTP_PROXY`。

**实测结果（重要，别夸大）**：写了 `Probe.cs` / `Probe2.cs` 用
`C:\WINDOWS\Microsoft.NET\Framework64\v4.0.30319\csc.exe` 编译后对照同步
`TcpClient.Connect` 的地面真值测：

| 情况 | `WaitOne(300)` | `WaitOne(3000)` |
|---|---|---|
| 端口在监听（7897） | **True** ✓ | True |
| 端口关闭（探测了 2 个） | **False** ✓ | **True** ✗ |

也就是说：**在这台机器上旧代码因为"失败完成得比 300 ms 慢"而恰好给出正确答案**。
这是**潜伏缺陷，不是已复现的故障**。同时实测确认 7897 **确实是活的**代理
（netstat：`TCP 0.0.0.0:7897 LISTENING pid 15104`）——
注意用 `Get-NetTCPConnection -State Listen -LocalPort 7897` 查会**误报**"没在监听"，netstat 才是准的。

**修法 [已修]**：等待后调用 `EndConnect`（惯用写法），语义不再依赖时序。
**结论：别把它写成"崩溃"或"必定误判"，那是夸大。**

### 2.8 `PickWorkingDirectory()` 会把**桌面**当成工作目录 **[已修]**

旧顺序：环境变量 → **exe 所在目录** → `D:\Deepseek Harness`。
而 `launcher/README.md` 教用户"复制 Exe 到桌面双击" —— 一叠加，**桌面成为 dsh 的工作目录**，
用户的项目产物会写到桌面上。

**修法 [已修]**：改成 环境变量 → exe 同目录的 `dsh-workdir.txt` 边车文件 →
`D:\Deepseek Harness`（存在时）→ exe 目录（**桌面除外**）→ 用户主目录；
`launcher/README.md` 也改成"别放桌面，建快捷方式"。

### 2.9 `NODE_OPTIONS=--use-env-proxy` 无条件设置 **[已修]**

那是 **Node 24** 才有的旗标，低版本 node 会以 `bad option: --use-env-proxy` 直接死掉。
本机实测 node **v24.18.0** 下 `node --use-env-proxy -e ...` 退出码 0（合法），
所以这台机器不会出问题 —— 但这是个**潜伏**的跨机故障。

**修法 [已修]**：加 `NodeMajorVersion(node)` 辅助函数，只在主版本 ≥ 24 时设置。

### 2.10 换行符：Windows 的 `core.autocrlf` 会把 `install.sh` 变成 CRLF，Ubuntu 上直接跑不起来 **[已修]**

本机 `core.autocrlf = true`。`git add` 时打出一片
`warning: ... LF will be replaced by CRLF the next time Git touches it` ——
其中就有 `install.sh` 与 `launcher/dsh-web.sh`。

**后果**：CRLF 的 shell 脚本在 Ubuntu 上 shebang 会变成

```
bash: ./install.sh: /usr/bin/env bash^M: bad interpreter: No such file or directory
```

报错信息**完全指不到"换行符"这个真因**，是极难排查的一类问题。
同理 `.py` 的 `#!/usr/bin/env python3\r` 也会坏。

**实际情况比想象更糟**：`git ls-files --eol` 显示
`scripts/cost_anatomy.py` 与 `scripts/verify_leash.py` 是 **`i/-text`** ——
git 的二进制启发式把它们当成二进制文件（**尽管文件里一个 NUL 字节都没有**）。
被当成二进制意味着**不做换行规范化、diff 也不显示**，于是这两份文件里各留了
**1 个 CRLF**（都在 `import _session_io as S  # noqa: E402` 那一行），
`git ls-files --eol` 报 `w/mixed`。

**修法 [已修]**，三件一起做：

1. 新增 `.gitattributes`：`* text=auto eol=lf`；
   `.ps1/.psm1/.psd1/.cmd/.bat` 用 `eol=crlf`；`.sh/.py/.mjs/.yml/.toml/.md/.cs` 用 `eol=lf`；
   `*.exe/*.dll/*.ico/*.png/*.lnk/*.db` 标 `binary`（否则会被换行转换搞坏）。
   **`.sh` 必须是 LF** 是这里最要紧的一条。
2. `git add --renormalize .`，把索引统一到 LF。
3. **把换行也纳入 `tools/check-encoding.mjs` 这道闸门**（原来只管 BOM）：
   同时检查"应该 CRLF / 应该 LF"和"混用"，`--fix` 可就地修正。
   首次运行报出 **25 处违规**（大量 `.md`/`.yml`/`.toml` 是 CRLF、两个 `.ps1` 是 LF、
   两个 `.py` 混用），修完复跑 OK，且**逐字节复验两个 `.py` 的 CR 数 = 0**。

> 为什么 `.gitattributes` 还不够：它管的是"入库/检出时"的规范，
> 而手改文件（尤其用带自动换行转换的编辑器或脚本）会把工作区又弄脏。
> 两者都要有，闸门才不会形同虚设。
>
> 反过来，**`.ps1` 一律 CRLF** 是契约的一部分：PowerShell 两种都读得懂，
> 但统一之后 `.ps1` 与 `.sh` 的差异一眼可见，减少"这个文件该是什么换行"的判断成本。

> ### 更正（2026-09-19，读源码后）
>
> 我上一条把 `modelSelectionSettings: true` 也归进"会少掉工具"，**这个说法不准确**。
> 实际读 `dsh-tool-subagent/lib/index.js`：
>
> ```js
> line 255:  modelSelectionSettings: z.boolean().default(false),   // tool-subagent 的配置键
> line 374:  const modelSelectionCapable = config.modelSelectionSettings === true;
> line 582:  if (config.modelSelectionSettings !== true) { install(ctx, void 0); return; }
> line 587:  // 为真时才去取 `subagentModelSelection` 设置面 + 走 subagentModelSelectionPolicy
> ```
>
> 也就是说它是**子代理的"模型可选"开关**：关着的时候子代理的 provider/model
> 完全由该行的 `agentOptions` 钉死；开着才允许子代理走 **Session 级模型选择**。
> 缺它丢的是"子代理可换模型"这个**能力**，不是工具。
>
> 这条对 `standard-leash` 有额外含义：leash 的护栏正是靠
> `agentOptions: {provider: deepseek-cheap, model: deepseek-flash}` 把子代理降档的；
> 若同时开 `modelSelectionSettings: true`，子代理的模型就变成用户可在选择器里改的 ——

### 4.11 `install.ps1` 把合并参数存进 `$args` → 第 5 步静默什么都没做 **[已修]**

`$args` 是 PowerShell 的**自动变量**（脚本自己的参数数组）。原来的写法：

```powershell
$args = $tplArgs + @("--target", $settings)
Exec "..." { & node $merger @args }        # @args 展开成空
```

赋值被自动值盖掉，`@args` 展开为空 → 合并器收不到 `--template`/`--target`，
**只打印了一行用法就退出 0**，而脚本把这当成成功。

**为什么干跑抓不到**：`-DryRun` 下 `Exec` 只打印描述字符串（那个字符串是拿 `$margs -join ' '`
拼的，看着完全正确），从不真正调用 node。**只有真部署才暴露。**
已改名 `$margs`。修好后真部署输出：
`[merge-settings] 目标: ... + 新增 provider: deepseek-cheap`。

### 4.12 `$ErrorActionPreference = "Stop"` + `2>&1` 让"未加固"把后续步骤整段带走 **[已修]**

`harden-preset --check` 在"未加固"时**正常返回 1** 并把说明写到 stderr。
而脚本顶部是 `$ErrorActionPreference = "Stop"`：

```powershell
& node $hardenScript $target --check 2>&1 | ForEach-Object { Say $_ }
```

native 命令往 stderr 写 + 被 `2>&1` 接进管道 → PowerShell 生成 `NativeCommandError`
→ 在 `Stop` 下**直接终止整个脚本**。实测后果：第 6、7 步（handoff / `AGENTS.md` /
`~/.dsh-analysis`）**完全没跑**，而末尾还打印"所有步骤成功"（因为终止不是走 `Fail` 路径）。

**修法 [已修]**：临时把 `$ErrorActionPreference` 降为 `Continue`、`try/finally` 复原，
并显式取 `$LASTEXITCODE` 判断，不再依赖管道行为。

> 这两条都是同一类问题：**干跑只能验证"打印了什么"，验证不了"真调用了什么"**。
> 结论：涉及外部写入的安装脚本，必须至少完整真跑一遍才算测过。

## 九、`reasoningEffort` 可用档位是**按模型**算的（本仓库曾把它当成全局事实）

### 9.1 现象：本机跑在 `low` 上，而文档说 `low` 会被拒

本机 `~/.dsh/settings.yaml` 里是：

```yaml
agent-default-model:
  provider: zai
  model: glm-5.3
  reasoningEffort: low
```

而本仓库多处（`README.md`、`config/settings.cost.yaml`、
`docs/2026-09-19-实测与更正.md`、`docs/交接体系.md`、`handoff/README.md`、
`handoff/CONTEXT.md`、`docs/DSH-成本与上下文治理.md`、`examples/…/INDEX.md`、
`scripts/effort_probe.py`）都写着"DeepSeek 适配器只放行 `off`/`high`/`max`，
`low` 会被拒绝"。**两者矛盾，于是查源码。**

### 9.2 事实：有两层，别混

**第一层 —— 适配器白名单**（`dsh-llm-deepseek/lib/index.js:28`）：

```js
function reasoningEffort(effort) {
  if (effort === "off" || effort === "low" || effort === "high" || effort === "max") return effort;
  throw new LlmError(`DeepSeek does not support reasoning effort "${effort}"`, "UNSUPPORTED_REASONING_EFFORT");
}
```

⇒ 这个适配器**接受 `low`**。旧文档说"只放行 off/high/max"**是错的**；
`medium` / `minimal` / `xhigh` 确实会被它拒绝。

**第二层 —— 真正的决定者：模型自己的 `thinkingLevelMap`**，
位于 `node_modules/@earendil-works/pi-ai/dist/providers/data/*.json`。
`dsh-llm-pi-ai` 把 settings 里的 `reasoningEfforts` 字典翻译成 pi-ai 的 `thinkingLevelMap`
（`dsh-llm-pi-ai/lib/index.js:548,583`）；没写就整份沿用目录里的默认值。

`null` 的语义有**消费端证据**（不是猜的）：

```js
// @earendil-works/pi-ai/dist/providers/azure-openai-responses.js:237
else if (model.thinkingLevelMap?.off !== null) { … effort: (model.thinkingLevelMap?.off ?? "none") }
// anthropic-messages.js:872 / openai-codex-responses.js:418 同构
```

⇒ **`null` = 该档位不可用**；有字符串值才是"可用，且这就是要发的 wire 值"。

### 9.3 本机实测（pi-ai `0.85.1`，随 dsh `0.1.5-rc.2` 安装）

| 模型 | `thinkingLevelMap` | **实际可用档位** |
|---|---|---|
| `glm-5.2` | `{"off":"none","minimal":null,"low":null,"medium":null,"high":"high","xhigh":null,"max":"max"}` | **`off` / `high` / `max`** |
| `glm-5.3` | `{"off":null,"minimal":null,"low":"low","medium":null,"high":"high","xhigh":null,"max":"max"}` | **`low` / `high` / `max`**（**没有 `off`**） |
| `glm-5.3-flash` / `-highspeed` | 同 `glm-5.3` | 同上 |
| `glm-5.1` / `glm-5-turbo` / `glm-5v-turbo` | `thinkingLevelMap` 未声明，`compat.supportsReasoningEffort: false` | 不可选档 |

两个 provider 目录（`zai.json` 与 `zai-coding-cn.json`）里 glm 的声明一致。

**⇒ 旧文档描述的其实是 `glm-5.2`。** 用户后来把默认模型换成了 `glm-5.3`，
档位集合就从 `off/high/max` 变成了 `low/high/max` —— 文档没跟上，于是看起来"自相矛盾"。

### 9.4 直接后果（可执行结论）

- **`"执行型会话用 off"` 这条规则在 `glm-5.3` 上无法执行。** 它没有 `off`，
  最低只能到 `low`。想要 `off` 必须换模型（`glm-5.2` 或 DeepSeek 线）。
- `high` 是默认档，写它等于没写。`max` 可用（记得显式压 `max_tokens`）。
- `medium` 在任何模型上都不合法，且**配置期不报错**：
  `dsh-agent-default-model/lib/index.js:16` 的 schema 只是 `z.string()`，
  `ReasoningEffortId()` 也是 `brandString(id)` —— 源码注释明说
  **"no validation is performed"**（`dsh-llm/lib/index.js:875`）。
  非法值要到**发请求时**才会按该模型的能力表抛出
  `UNSUPPORTED_REASONING_EFFORT`（`dsh-llm/lib/index.js:2120,2124`）。
  ⇒ **写错档位不会在启动时报错，只会在那一轮对话里炸**，所以必须靠文档而不是靠拼写检查。
- **档位可以按会话切**：`dsh-api-session-controller` 的 `selectModel(request)`
  会"Validate and install one Session-local model selection"，
  并把 `provider + model + reasoningEffort` 一起通过
  `agentDefaultModel.saveSelection(selected)` 存成新默认。
  **`dsh --help` 里没有任何 `--effort` 之类的 CLI 开关**。

### 9.5 版本问题（回答"是不是本机 dsh 版本太低"）

**不是。** `npm view @deepseek-ai/dsh dist-tags`：

```
{ "next": "0.1.5-rc.2", "latest": "0.1.5-rc.2", "alpha": "0.1.6-alpha.2" }
```

本机就是 `latest` = `next` = **`0.1.5-rc.2`**，即"最新的非 alpha 版本"；
比它新的只有 `0.1.6-alpha.1` / `0.1.6-alpha.2` 两个 **(alpha)**。
所以档位差异**不是版本低造成的**，而是**模型换了**。

### 9.6 系统性教训（这条比上面任何一条都重要）

本仓库所有的约束都只标注了**源码文件路径**，从不记录**验证所依据的 dsh 版本**。
而 dsh 是 `-rc` / `-alpha` 流水线，模型目录（`@earendil-works/pi-ai`）随版本更新 ——
一句"适配器只接受 X/Y/Z"过几个版本就可能变成假话，而且**没有任何机制会提醒你**。

**改进 [已做]**：
1. 凡是档位/能力类的断言，一律写成 **"哪个模型的哪几档"**，并附**证据文件 + 行号**，
   不再写成"适配器只接受…"这种看似全局的句子。
2. `README.md` 顶部增加"本仓库的验证基准"（dsh / pi-ai 版本 + 核查日期）。
3. `tools/check-encoding.mjs` 之外，`tools/regen-standard-leash.mjs --check`
   已把 dsh 版本写进 `presets/standard-leash/SOURCE.txt`；
   凡是从"当前安装的 dsh"派生的产物都带指纹，**升级后一跑就会报漂移**。
4. 自我更正：我在 §4.6 曾把 standard 副本缺 `modelSelectionSettings: true`
   说成"少掉工具"，**那是不准确的** —— 它是 `tool-subagent` 的"子代理模型可选"开关
   （`dsh-tool-subagent/lib/index.js:255,374,582`），丢的是能力不是工具。已在 §4.6 就地更正。

### 9.7 补充：`off` 的两种写法是**相反**的（极易写错）

比 §9.2 更细的一层，读 `dsh-llm-pi-ai/lib/index.js:539-590` 的
`resolveModelReasoning()` 得到。**同一个 `off: null`，在两种格式里含义相反**：

| 格式 | 出现在哪 | `off: null` 的含义 |
|---|---|---|
| `reasoningEfforts` 字典 | **你写的** `settings.yaml` 里 | **`off` 可用**，且"不发任何 thinking 参数" |
| `thinkingLevelMap` | pi-ai 的**目录 JSON**里 | **`off` 不可用** |

源码 docstring 原文（这是权威解释，不是我推的）：

> A declared dict translates to pi-ai's `thinkingLevelMap` with every level decided
> explicitly: declared levels carry their wire spelling, undeclared levels are pinned
> to `null` (unsupported). … A declared `off` with no value is the one exception:
> **it stays absent from the map, which pi-ai reads as "supported, send nothing"** —
> the correct dispatch where not thinking is the parameter's absence — while `off`
> with a value sends that value.

对应的实现：

```js
const map = {};
for (const level of THINKING_LEVELS) {
  const wire = efforts[level];
  if (wire === void 0) map[level] = null;      // 未声明 → 写成 null（不支持）
  else if (wire !== null) map[level] = wire;   // 有值 → 就是该 wire 值
  // wire === null 且 level === "off" → **不进 map**（缺席 = 支持且不发参数）
}
```

⇒ 结论：**在 settings 里，"关思考"必须写 `off: null`**（这正是
`config/settings.deepseek-cheap.yaml` 的写法，也是它跑得通的原因）；
而在目录 JSON 里要表示"支持关思考"得写 `off: "none"`（如 `glm-5.2`）。
**把目录里的 `off: null` 读成"参数为空"就错了。**

### 9.8 原生路由 `deepseek-official` 的档位不走目录

`deepseek-official` 由 `dsh-llm-deepseek` 自己注册
（`lib/index.js:1840` `const PROVIDER = "deepseek-official";`），
**它的能力表不在 pi-ai 目录里**，而是写死在库里：

```js
// dsh-llm-deepseek/lib/index.js:1417
const REASONING_EFFORTS = [ off, low, high, max ];   // 四个档
// :1595  rationale: 非 disabled 部署 → efforts: REASONING_EFFORTS，defaultEffort 回落到 high
// :1592  若部署级 thinking === "disabled" → efforts: OFF_ONLY_REASONING_EFFORTS（只有 off）
```

其模型清单（`lib/index.js:1842` `DEFAULT_MODELS`）：
`deepseek-flash`（名 DeepSeek-V41-Flash，text+image）、`deepseek-v4-flash`、
`deepseek-v4-pro`、`deepseek-v4-flash-vision-exp`。
**四个模型统一拿到 `off`/`low`/`high`/`max`。**

> ⚠️ 别把目录里的 provider **`deepseek`**（`data/deepseek.json`）和它混为一谈：
> 那是 **pi-ai 路由**，`deepseek-v4-flash` 只声明 `low`/`high`/`max`，**没有 `off`**；
> `deepseek-v4-pro` 只有 `high`/`max`。名字像，能力不同。

`tools/show-effort-levels.mjs` 已内置这条原生路由的知识（常量 `NATIVE_ROUTES`），
否则它读目录会报"找不到 deepseek-official/deepseek-flash"。
